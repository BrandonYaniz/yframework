# Recovery State and Task Selector Repair

## Why this is required

The checked-in `.codex/STATE/completed.md` presently contains five headings (001, 009, 012, 017, 018) with descriptions that do not always match original task titles and some implausible commit hashes. Earlier history contained 001 through 018 plus 023. `scripts/next-task.py` currently reads task headings with `COMPLETED_RE`, then considers tasks done solely because a heading exists. This can skip unmet prerequisites. The checked-in `.codex/CURRENT_MILESTONE.md` remains at Task 001, and `.codex/STATE/v1-progress.md` incorrectly asserts Milestone 1 is completed. All of these must be reconciled from evidence.

## Recommended verified-state record (new file, not prepopulated with invented status)

Choose a simple tracked format such as `.codex/STATE/verified-tasks.json` for *machine-readable* status, with a separate Markdown evidence log. Suggested per-task structure:

```json
{
  "schema_version": 1,
  "tasks": {
    "001": {
      "status": "unverified",
      "verified_commit": null,
      "evidence_file": null
    }
  }
}
```

Valid states: `not_started`, `unverified`, `incomplete`, `blocked`, `verified`. A real `verified` status must include an existing commit SHA and a path to recorded acceptance evidence. **The above is an example schema proposal, not a claim that Task 001 was verified.** Only introduce it after reviewing consistency with existing task-control requirements.

## Recovery requirements

1. Save pre-repair completion records with exact source provenance. Never fabricate hashes. Existing commits might be recoverable from Git history.
2. Compare task heading, original task title, declared predecessors, tested behavior, completion log, and actual source. Flag discrepancies explicitly.
3. Refactor task selection to use only *verified* task states for dependency satisfaction; retain the original task filenames, milestone IDs, and explicit dependency graph.
4. Add selector tests with malformed/missing state, incomplete historical heading, non-existent referenced commit, and unmet prerequisites. Missing verified state must fail closed.
5. The selector must never report all 881 tasks complete merely because 881 headings exist. The pipeline should report blocked/verification-needed when proof is missing.
6. Update `CURRENT_MILESTONE.md` only after the appropriate acceptance gate passes. Fix `v1-progress.md` to reflect actual status.
7. Preserve `.codex/STATE/open-decisions.md` and record only genuine architecture-affecting blockers, using `DECISION_AUTHORITY.md`.
8. Protect local environment details. Keep secrets out of tracked state. Review `.codex/STATE/local-environment.md` and its Git history for sensitive content.

## Reconciliation acceptance checks

- Historical log is retained as attempted/completion history, not a trusted proof source.
- A test with `completed.md` containing `## Task 023` but no verified 021/022 must still block 023/024.
- A test with a fake commit SHA for 017 must not declare 017 verified.
- A stale `CURRENT_MILESTONE.md` must be corrected after gates pass, and never ahead of them.
- `next-task.py --status`/`--json` clearly report verified vs attempted and recoverable blockers.
- Existing 881 tasks and their settled source references are left unchanged unless a specifically reviewed correction is required.

## Never do this

- No wholesale deleting `.codex/STATE` or replacing historical logs with autogenerated success entries.
- No fake `go test` counts, fabricated hashes, or boilerplate `Architecture: no unresolved decision` without review.
- No adding an entry to `completed.md` for a failed, skipped, or partially implemented task.
- No treating `.codex/STATE/recovery-fixes.md` as proof when source contradicts its claims.
